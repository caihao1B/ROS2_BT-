# S02 技术说明：连续三维世界与先验分层

本阶段交付可复现、可观测的场景基础。两个工作区是完整凹多边形；内部没有人为预设的三簇、围墙或沟渠。S11 再按实际工作量做连通分簇，S12 根据路径与工时复核每簇 30 分钟预算。S02 的短时测试不等于作业任务完成。

## 技术选择及边界

| 问题 | 本步选择 | 优点 | 代价/限制 |
|---|---|---|---|
| 场景制作 | Python 参数生成 SDF + 本地 OBJ | 坐标与版本一致；无需远程模型下载；资源很小 | 外观简化，无真实植被/材质统计 |
| 不规则边界 | Shapely 2.1.2 Polygon，约束 Delaunay 三角化 | 凹口与孔洞保留；可检查面积和连通性 | 几何合法不等于车辆可通行 |
| 道路 | 两段切向连续三次 Bézier，中心线缓冲 3 m | 可保存弧长、检查点、道路边界 | 不保证曲率满足阿克曼；留 S03 验证 |
| 三维地形 | 5°/10°/18° 双坡楔体，同源 visual/collision 网格 | 传感器和物理看到同一坡面 | 是可重复测试地形，不是土壤沉陷模型 |
| 移动物体 | 4 个轻量几何行人 + 1 台移动设备；C++ 理想速度执行器 | 固定种子可复现；支持实际接触与传感器成像 | 无步态、人群互动、学习预测；执行器会覆盖部分外力效果 |
| 可用信息分层 | 公共先验 + ROS 119 传感器；ROS 120 独立评估 | 真实数据流可检查，不向在线算法输入精确物体位置 | 同一用户仍可直接读磁盘或 Gazebo Transport；不是 OS 安全沙箱 |
| 渲染 | Gazebo Harmonic Ogre1 | 本机实际 RGB 色彩正常、GPU 雷达可用 | 原系统 Ogre2 GUI 曾有白材质问题；并非所有机器都应固定 Ogre1 |

## 坐标、尺寸与生成原理

世界 160×112 m，局部 ENU、z 向上，单位 m，原点 (0,0,0)，frame 为 `map`。尚未指定经纬度 datum；后续 GNSS 阶段再配准，不能把局部 GeoJSON 坐标解释成 WGS84 经纬度。`map_metadata.json` 明确注明坐标系。

基础喷洒区 1650 m²、割草区 1140 m²。这是边界面积（含洞时已扣除洞），尚未扣除边界内其他已知设施；覆盖规划需用 permanent 层进一步求可作业面积。顶点围成凹多边形后，围绕质心按 `s = sqrt(A_target / A_original)` 等比缩放，再平移到指定区域。凹口变体从边界减去矩形；含洞变体从内部减去 6×4 m 固定设施岛，剩余作业区仍然连通。

道路采用 `B(t)=(1-t)^3 P0+3(1-t)^2t P1+3(1-t)t² P2+t³ P3`，两段连接处切线一致，离散为 162 点，再缓冲成 6 m 宽道路。中心线约 88.48 m，存 9 个检查点。当前连接路平坦，保存的高程和坡度为 0；三种坡地位于工作区内部。S03 需要实际足迹扫掠、曲率和动力学检查，不能只用宽度证明能通过。

俯视 GUI 的 near/far 裁剪范围为 2/500 m，地面 GUI 为 0.1/500 m，防止大地图毫米级叠加面在远距离产生深度闪纹；这不改变传感器的真实近距参数。边界和道路的渲染面只比物理地面高 6/12 mm，不生成额外物理台阶。设施、低障碍、人体各部件和设备各部件的碰撞体与可见几何/局部变换逐一一致。OBJ 显式生成面法向量；缺失法向曾触发本机 DART/ODE 网格加载崩溃，本版已修复并做实际加载测试。

## 先验与未知信息的责任边界

```text
离线生成器 → assets/worlds + evaluation/truth_manifest → Gazebo 物理/渲染
          └→ maps/prior → 在线节点（ROS domain 119）
Gazebo → 时钟 / 3D 点云 / RGB → 在线节点 → 观测快照
Gazebo → 动态真值 / 接触 → 独立评估（ROS domain 120）
观测快照 + 真值 → 离线报告；报告不再作为在线输入
```

先验含工作边界、道路、永久设施禁行几何、已知粗地形格。未知部分含 0.08/0.15/0.30 m 临时障碍、动态物体、细坡面。粗地形仅给 3 m 分辨率区域与 0–8° 坡度带、3° 不确定性，不给精确网格。改变隐藏对象的随机种子不会改变任何公共先验文件。SDF 必然含真实物体，这是模拟器的输入，不是规划器输入。

临时固定探针位于 (20,25,1.1)，偏航 0：3D GPU 雷达 512×64、10 Hz、0.08–40 m；RGB 640×360、5 Hz、HFOV 1.4 rad、向下俯仰 0.08 rad。探针有已知固定外参，用于场景验证。本步无机器人 TF 发布者、无车辆控制、无融合定位。镜头/点云都从 Gazebo 实际渲染取得，尚未注入商业传感器噪声、时间漂移或天气退化，S04 完成这些设计。

离线评估将三维回波变换到 map，再与物体实际包络比较，计数雷达命中；将包络投影到 RGB，并检查指定色块是否出现。这只是模型可观测性检查，**不是训练出的目标检测、分割或语义融合算法**。远处行人在固定探针视距外出现 0 次命中是合理现象；验收目标只包含视野内三类低障碍、近处行人和设备。

## 动态模型与反馈

每个物体使用种子生成初始相位 φ，轨迹为 `x=cx+ax sin(ωt+φ)`、`y=cy+ay sin(2ωt+2φ)`，ω=2π/T。C++ 插件使用 Gazebo 的仿真时间计算目标位置/速度，并用实际 link 世界位置闭环修正：`v_world = v_reference + 2*(p_reference-p_actual)`，速度上限 2 m/s。转换到 link 坐标后调用 `SetLinearVelocity`，角速度使物体保持直立。

模型是动态刚体，碰撞交给 Gazebo；专用验收场景加入质量 2 kg 的被动方块，检查行人接触对和方块位移。名义场景不包含这个验收夹具。由于是理想速度驱动，不能用该测试推导真实人体受力、车辆制动安全或动态避障成功率。S15 的预测需要使用传感器提取的轨迹，禁止直接订阅本插件发布的未来函数/真值。

指标说明：当前报告的 `active_rtf` 字段按“仿真时长 / 观测器存活的现实时间”计算，包含订阅就绪和启动等待；它是整段采集的保守耗时比，不能当作 Gazebo 稳态 WorldStats 的实时率。

## 版本、依赖和复验
