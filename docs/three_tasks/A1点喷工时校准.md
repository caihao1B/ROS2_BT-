## 离线规划怎样计时

R03 为每段计算路程除以 0.4 米/秒，加上累计绝对转角除以 0.4 弧度/秒，再加 2 秒。56 次点服务另加每点 3 秒。逐段累加后，平移段名义合计 538.213 秒，转向段 241.591 秒，点服务段固定开销 112 秒，作业动作另占 168 秒。把这四项之和乘 1.25，再加固定 60 秒，得到整簇 **1,384.755 秒**。最后一个服务点之后还有折合 19.284 秒的名义路程。表中的“同一前缀”用这个公式截到最后一个已确认点，不把后续点和这段返程算进去。使用前缀避免拿整簇预测和部分任务直接相减。[R03 分段与计时源码](../../optimization_v2/ws/src/task_platform/scripts/planning_r03.py) · [原始任务](../../optimization_v2/three_tasks/editions/R03/mission.json)

R10 实际点喷的任务上限为 0.30 米/秒和 0.35 弧度/秒。Nav2 的 RPP 目标线速度为 0.30 米/秒，转弯、接近目标和制动会进一步减速。导航到点后，任务还需停稳，验证定位窗口，必要时发出局部精停目标，然后等待工具服务器和账本。原公式为段开销给了统一时间，这些操作的实际成本随点位和观测条件变化。每次为什么多花时间，应按点查看事件后再归因。[R10 控制器](../../optimization_v2/three_tasks/editions/R10/spray/nav2.yaml) · [任务版本与底盘参数](../../optimization_v2/three_tasks/editions/R10/spray/mission.json) · [点喷执行器](../../optimization_v2/ws/src/task_platform/scripts/mission_spray_r10.py)

## 怎么复算，怎样读数

从仓库根目录执行。Python 只使用标准库。Windows 上已安装 Python 时可将命令开头的 `python3` 替换为 `py -3`，直接读取随仓库附带的观测。

```bash
python3 optimization_v2/three_tasks/spray_time_budget.py
python3 -m unittest discover -s optimization_v2/three_tasks -p test_spray_time_budget.py
```

第一条输出 JSON，`point_cycles` 每行有点编号、上一确认至本点结束的时长、首次接受导航的时刻、是否确认及各阶段时长。`common_confirmed_prefix` 只比较两次都已按序完成的点。`without_accepted_goal` 列出日志中尚未收到导航受理事件的目标，`attempted_unconfirmed` 单列已受理却没有完成回执的目标。第二条运行四个回归用例，覆盖重复请求、取消、尚未关闭的账本预留、未完成点和计划末尾的返程。[计算脚本](../../optimization_v2/three_tasks/spray_time_budget.py) · [用例](../../optimization_v2/three_tasks/test_spray_time_budget.py)

在保存有完整原始工作目录的 Linux 机器，还可以从本机重新提取证据。以下两行仅打印 JSON；重定向到本机 `/tmp` 便于比较，运行中重复提取只代表当时的快照。

```bash
RUNS=optimization_v2/three_tasks/results/R12
python3 optimization_v2/three_tasks/spray_time_budget.py --capture \
  --run "$RUNS/spray_20261115_060145_047614" \
  --run "$RUNS/spray_20261119_081218_417252" > /tmp/a1-observations.json
python3 optimization_v2/three_tasks/spray_time_budget.py \
  --observations /tmp/a1-observations.json > /tmp/a1-time.json
```

计时分配遵循以下口径。各段互斥，初始化和四类工时之和等于观察截止的仿真时间。

| 类别 | 计时边界和局限 |
|---|---|
| 初始化 | 从仿真时钟零点至第一个已受理的 `NAV_GOAL`。另列 Nav2 生命周期就绪时刻。 |
| 全局导航 | 从收到导航动作受理，到到点/精停交接或已记录的中断。动作内部的减速和某些停稳等待也在其中。 |
| 精停 | 从到点或提前停止、转入精停到工具开始预留，包含静止观测窗口和局部对接。遇到明确恢复事件则暂停计入本类。 |
| 工具 | 从 SQLite `transitions` 的 `RUNNING` 到对应终态。包括导致取消的预留、确认等开销；实际有效喷洒量与该时长区别计量。 |
| 等待、恢复和交接 | 当前没有已记录的导航、精停或工具预留时段，涵盖重新许可、定位恢复、记录换点和终止清理。单凭这列无法区分静止、行人避让或传感器异常。 |

同一任务多次发送目标不会重置计时。仅同时满足工具成功、剩余量为零、无待定误差、非重放的第一条结果计为完成。已关闭任务还核对最终 `mission_result` 的逐点清单，以及 SQLite 的 `SUCCEEDED` 顺序。原始事件、任务文件、规约和账本选定行的指纹随快照存档。已完成点的中位数与 P90 采用线性插值，按点计数。最后一次未确认尝试不进入已完成点的分位数，但消耗的时间完整保留在工时总表。中位数之和通常与总周期中位数不同，两个不同版本的运行也不能单独证明某项改动的因果效果。

## 如何把结果用于将来派工

在每个确认点之后，计算剩余预算 `1800 − 当前仿真秒数`。先保留本次现场需要的安全停止、账本提交及撤离时间，再用剩余可工作时间评估未用点。报告中的“剩余点要求的平均秒数”把安全保留暂取零，是算术门槛；若已经到时，真实可继续派工的数目还取决于现场规则。已完成前缀里的中位数、P90、慢点记录和剩余路线特征可以作为下一次拆簇的输入。一个前缀的样本有顺序偏差，不能用 P90 推成整簇成功概率，给未执行的点预先记账，或把 R03 的固定 60 秒直接认作已验证的安全停车时间。

查看残余义务时，用工具账本和任务终态核对；这份工时分析保持所有验收条件原样。可结合回放定位耗时的阶段，割草区域使用面积工具另行计算。[三任务残余复核工具](../../optimization_v2/three_tasks/residual_review.py) · [新手观察路线](第一次观察三任务.md)
